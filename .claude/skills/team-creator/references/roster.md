# 团队角色目录（Team Roster）

技能向用户展示的可勾选角色清单。每个角色对应一个 Claude Code 子 agent 定义。

## 如何使用本文件

- 用户通过问答表单勾选所需角色，并为部分角色指定数量（如后端工程师 3 名）。
- 只有被勾选的角色，才会生成对应的 `.claude/agents/<agent-type>.md`、出现在协作规范文档里、并在即时启动时被 spawn。
- 没勾选的角色，全程不出现——包括团队列表、任务派发选项、协作文档里都不会提。

| 系统架构师 | `system-architect` | 1 | 整体架构设计、技术选型、数据模型设计、接口契约定义、非功能性方案(性能/可用性/扩展性/一致性)、架构评审、技术风险评估 |
| 后端高级开发工程师 | `java-backend-eng` | 1~N | 后端开发任务；防御性编码 + 复用优先 + 自测义务；BUG 走完整闭环（含根因与经验沉淀）。详见下文"开发工程师质量职责" |
| 前端高级开发工程师 | `frontend-eng` | 1~N | 前端开发任务；防御性编码 + 复用优先 + 自测义务；BUG 走完整闭环（含根因与经验沉淀）。详见下文"开发工程师质量职责" |

## 开发工程师质量职责（后端 / 前端通用）

开发工程师（`java-backend-eng` / `frontend-eng`）的职责不止"把功能写出来 + 修 BUG"，而是要在编码阶段就**主动防 bug**，并在修 BUG 时做**根因沉淀**。这四项是硬要求，写进 agent 定义正文和 spawn prompt：

- **防御性编码**：边界条件、空值/异常路径、并发安全、资源释放，在编码时主动处理，不留"以后再说"。典型反例：只测正常路径、忽略空列表、忘记关闭连接。这些是提测前就该消灭的低级 bug。
- **复用优先**：动手实现前先搜代码库是否已有类似实现/工具函数/组件，**禁止重复造轮子**。重复实现是"修了一处忘了另一处"类 bug 的主要来源（呼应 code-refactorer 的职责，但前移到编码阶段——预防比事后去重成本低得多）。
- **自测义务**：交付前跑通单元测试 + 自己走一遍主路径和边界场景，**提测前消灭低级 bug**。不要把"代码能编译"等同于"功能能用"。自测发现的问题不算测试的锅，提测后被测试打回来才是。
- **BUG 修复走完整闭环**：收到测试提的 BUG，不止"改到能跑"，必须做根因分析（为什么会发生、归入哪个根因类别）+ 经验沉淀（写入 `docs/lessons/`）。对接 SKILL.md BUG 闭环的第 4、7 步。只修不复盘，同一个坑会在别处再犯。
- **偏好遵循**：实现前先查 `docs/preferences/` 与本任务相关的条目，**主动遵循用户已认可的风格**。这和"复用优先"（复用代码）同源——复用代码避免重复造轮子，复用偏好避免重复纠正。若用户的本次要求与已有偏好一致，直接遵循并说"按你之前认可的方式做了"；若与某条偏好冲突，先提出来确认，不要默默违背。

## 测试工程师质量职责

测试工程师（`test-engineer`）的职责不止"执行用例 + 提 BUG"，而是要织一张**随项目增长的防线网**，让过去的坑变成永久的兜底：

- **回归用例库**：维护一份随项目增长的回归用例集，每次代码变更回归跑一遍，**防止"修 A 坏 B"**。回归网越密，越不怕改老代码。
- **bug→用例转化**：每个修复的 BUG 必须转化为一条回归用例，加入回归库（对接 SKILL.md BUG 闭环第 6 步）。**让过去的坑变成永久的网**——这是测试从"点状打靶"变"网状兜底"的关键。
- **同类排查**：收到 BUG 时不止测当前场景，按根因模式在代码库**主动搜同类隐患**（同模式调用、同类边界），开新条目或并入（对接闭环第 5 步）。测一点发现一片，比逐个救火高效。
- **测试左移**：在需求/设计阶段就介入，从验收标准反推测试用例，**边界条件在编码前就定义清楚**。需求分析师定义"做什么"，测试工程师定义"怎么算对、哪些边界要兜"，工程师照着实现——bug 在写代码之前就被设计挡掉一部分。

## UI 设计师偏好职责

UI 设计师（`ui-designer`）的视觉/交互偏好高度个人化，是偏好学习的**重点角色**。职责不止"出设计稿"，而是要积累用户审美记忆，从"每次重新猜用户审美"转向"稳定输出用户认可的风格"：

- **出稿前先查偏好库**：每次出设计稿前，先查 `docs/preferences/` 里与本任务相关的 UI/视觉、交互类条目，**主动遵循用户已认可的风格**（布局、配色、间距、组件用法、交互方式）。不要每次都从零猜——用户上次认可的配色/布局偏好，本次应直接套用并说"按你之前认可的风格出稿了"。
- **视觉偏好沉淀**：用户对设计稿的每次认可/纠正，**主动**沉淀为 `docs/preferences/` 条目（标明哪个页面、用户怎么说、认可/纠正的是什么）。下一次出稿前先查，**避免用户反复就同一类视觉问题纠正**。对接 SKILL.md 领导行为第 9 条。
- **与前端协同**：视觉偏好不只影响设计稿，也影响前端实现。UI 工程师把沉淀的视觉偏好通过 SendMessage 同步给前端工程师，确保前端实现与用户认可的视觉风格一致，而非各自发挥。



每个角色的 `.claude/agents/<agent-type>.md` 需包含 YAML frontmatter。**文件最顶端**（frontmatter 之前）先写版本指纹，用于第 -1 步判断产物版本、决定要不要升级：

```markdown
<!-- generated-by: team-creator v2 -->
---
name: <agent-type>
description: <一句话职责 + 触发场景。说明"当任务涉及 X 时，委派给此 agent">
tools: <工具集，见下>
model: inherit   # 继承当前会话模型，除非用户另行指定
---
```

### 正文质量五项（工程师/测试/UI agent 必含）

frontmatter 之后是 agent 的职责正文。对于**开发工程师**（后端/前端）、**测试工程师**和**UI 设计师**的 agent 定义，正文除了写角色职责清单 + "与团队其他成员通过 SendMessage 实时沟通"，**必须**包含"质量五项"，让每个实例 spawn 出来就带着质量意识 + 偏好意识：

- **复用优先**：实现前先搜已有实现，禁止重复造轮子。
- **自测义务**：提测前跑通单测 + 自走主路径和边界。
- **缺陷闭环**：修 BUG 走完整 7 步（救火 + 防火），不止"改到能跑"。
- **经验沉淀**：根因写入 `docs/lessons/`，把这次的坑变成团队的记忆。
- **偏好遵循 + 认可即沉淀**：实现/出稿前先查 `docs/preferences/`，主动遵循用户已认可的风格；用户认可或纠正某风格时，主动沉淀一条新偏好到 `docs/preferences/`。复用代码避免重复造轮子，复用偏好避免重复纠正。

> 团队-creator 在第 3 步生成 agent 定义、第 5 步 spawn 时，从上文"开发工程师质量职责"/"测试工程师质量职责"/"UI 设计师偏好职责"把对应内容摘录进 prompt，确保每个实例都装载这五项。详见 SKILL.md BUG 闭环章节与领导行为第 1、9 条。

### tools 字段约定（权限分级设计）

工具集不是随便给的，它要和角色的**职责边界**严格匹配。核心原则：**会改代码的角色给全权限，只审查/分析的角色给只读权限**。这样既保证该干的能干，又避免越权瞎改。

| 权限级 | tools 配置 | 能做什么 | 不能做什么 | 适用角色 |
|---|---|---|---|---|
| 全权限 | `All tools` | 读、写、改代码，跑命令/测试，搜索 | — | 后端、前端、测试、代码审计、UI、架构、需求 |
| 只读分析 | `Read, Grep, Glob, WebSearch, Write` | 读代码、搜索、联网查、写报告 | 改代码（无 Edit）、跑命令（无 Bash） | 安全审计 |

**为什么安全审计是只读（设计理由）**：审计和修复分离。安全审计发现漏洞 → 写报告 → 派给对应工程师修。如果审计者自己改代码，它既当裁判又当运动员——审出的"修复"没有第二双眼睛把关，而且审计者未必熟悉被改模块的全局上下文，容易引入自己看不到的盲区。所以**写代码的活儿路由给工程师**，审计只负责"发现和验证"，`Write` 仅用于输出审计报告。

**为什么工程师必须全权限**：后端/前端工程师的职责就是实现功能、修 BUG、写测试，需要 `Edit`/`Write` 改代码、`Bash` 跑构建和测试、`Read` 读契约和规格。给它们只读权限等于让它们"无法编程"，角色就废了。

**派活时的权限意识**：领导给某角色派任务前，要先确认任务需要的工具它有没有。比如派安全审计"修复这个漏洞"就是错的——它没 Edit，应该派"审查这个漏洞并出修复建议"，真正的修复派给工程师。这呼应 SKILL.md 的"派发前先确认输入齐全"原则——输入包括工具能力。

**重要：别被模型的自述误导**。实测中曾出现某角色（配的是 `All tools`，本该有 Read）声称"自己没有文件读取工具"。这是 LLM 偶发的**工具权限幻觉**——模型误判了自己的能力，不代表它真没权限。遇到成员说"我没这个工具"时：
1. 先查它的 `.claude/agents/<name>.md` frontmatter 里 `tools` 实际配了什么，以文件为准。
2. 如果文件里确实有该工具，是模型误判，让领导把所需内容摘录直接发给它绕过（不必纠结），或重新 spawn。
3. 如果文件里真没有，那才是真权限不足，按上面的"派活权限意识"重新路由任务。


### 多实例角色的命名

当某角色数量 > 1（如 3 名后端工程师）时，即时启动阶段为每个实例分配可寻址名称：
`<agent-type>-<序号>`，例如 `java-backend-eng-1`、`java-backend-eng-2`、`java-backend-eng-3`。
领导通过 `@java-backend-eng-2` 派发任务，成员之间用 SendMessage 互发消息时也用这些名字。

## 角色协作关系（用于求证/反驳路由）

跨领域求证时，领导应把问题路由给最相关的角色对：

- 接口/数据模型争议 → 架构师 ↔ 后端 ↔ 前端
- 安全相关缺陷 → 安全审计 ↔ 对应工程师（后端/前端）
- 代码质量/重复 → 代码审计 ↔ 对应工程师
- 验收/边界争议 → 需求分析 ↔ 测试 ↔ 对应工程师
- 视觉/交互争议 → UI 设计 ↔ 前端

相互反驳、保留最后一个存活的结论——即在所有反驳尝试都失败后仍未被推翻的那个结论，才作为最终采纳结论。
