# 验收检索中花括号 glob 模式静默失配，"零命中"险被当通过

- 根因类别：其他
- 状态：已修复·已沉淀
- 相关模块：docs/refactor/acceptance.md（验收检索脚本）、领导抽验流程（Grep 工具 glob 参数）

## 现象 / 复现

去 picc 化重构（2026-09-10），三片落地后领导做逐目录独立 grep 抽验。为一次覆盖多个目录，使用了花括号组合 glob 模式（形如 `{a,b}/**`）传给 Grep 工具——工具正常返回、零命中，无任何报错或警告。该结果若单独采信，等于"全库干净、验收通过"；与工程师自检结论交叉比对后才确认是**模式失配的空跑**，并非真的零命中（幸两侧结论一致，未酿成误判）。

静默性是本坑的核心危险：glob 匹配不到任何文件不是错误状态，工具把它当作"合法的空结果"正常返回，调用方从输出形态上无法区分"真干净"与"没搜到"。

## 根因

Grep/Glob 类工具的 glob 参数对花括号展开 `{a,b}` 的支持不一致（部分实现按字面量处理，`{a,b}/**` 匹配的是名为 `{a,b}` 的目录，自然命中为零）。而"零命中"在本类验收语义里恰是**通过判据**——检索器的静默失败与验收的通过条件同向，失去了天然的可疑性。本质：**把"集合选择"职责塞进了模式语法层，而该语法层能力未被验证**。

## 同类隐患排查

- 全量核查 `docs/refactor/acceptance.md` 的全部检索命令：`grep -rilE "picc|eureka|tongweb"`（多关键词走正则交替）、`find . \( -iname ... -o ... \)`（多谓词 OR）、`--include=pom.xml`（单模式）——均为朴素模式，无一使用花括号组合，不受影响；
- 测试侧终验实际执行的同款命令（含动态路径 `find server -maxdepth 1 ...`）同样朴素模式，终验结论可信；
- 潜在同类场景：任何把"多目录/多后缀集合"交给工具 glob 参数的用法（Grep/Glob 工具的 `glob` 参数、命令行工具的花括号路径）。

## 修复要点

非代码 bug，修复在约定层：验收检索命令一律采用朴素模式（逐目录调用或 `**` 单形态），多关键词交给正则交替（`grep -E "a|b|c"`）而非模式组合。`acceptance.md` 第三节一键回归脚本现行为安全形态，作为活样例维护。

## 回归用例

沉淀为验收执行规范（本条），并在后续所有"零命中=通过"类验收（如 AC-1/AC-2）执行时附带**阳性对照**：用已知应命中的样本（如白名单文件 application.yml 的 `GDpicc!2020`）先正向跑同一命令，证明检索通路有效，再采信其零命中结论。本次终验的 AC-1 恰 3 处白名单命中，事实上构成了该阳性对照。

## 防范措施

1. **全量 grep 复核禁用花括号组合模式**：用逐目录多次调用或 `**` 朴素模式；多关键词用 `grep -E "a|b|c"` 正则交替；
2. **零命中判定前先做阳性对照**：凡"0 命中即通过"的检索验收，必须先用已知应命中样本验证同一命令能命中（先证明检索器活着，再相信它的沉默）；
3. **双路径交叉验证**：抽验与自检结论一致才放行——本次实际生效的机制，保留为标准动作；
4. 工具 glob 参数只用于单形态过滤（`*.java`、`**/*.xml`），目录集合选择用 `path` 参数逐次指定。
