# 版本号语义：四段式，前两段对齐 Spring Boot，第三位承载破坏性变更

- 分类：沟通/流程
- 状态：已认可
- 适用范围：本仓库全部发布版本号（jevokit-parent / jevokit-dependencies / 全部 starter）

## 偏好描述

版本号四段式 `A.B.C.D`，各段语义：

| 段 | 含义 | 说明 |
|---|---|---|
| 第 1、2 段（A.B） | 对齐 Spring Boot 版本线 | 如 `3.5` ⇔ Spring Boot 3.5.x；Spring Boot 升大版本时本库跟随升前两段 |
| 第 3 段（C） | **本项目的破坏性变更位** | 破坏性变更（配置前缀、API、自动装配行为等不兼容改动）时 +1，第四位归 0 |
| 第 4 段（D） | 本项目的常规迭代位 | 功能新增、bug 修复、依赖升级等兼容性变更时 +1 |

例：`3.5.0.0`（首发）→ 常规迭代出 `3.5.0.1` → 配置前缀 `spkit.*` 改 `jevokit.*`（破坏性）→ 下一版打 **`3.5.1.0`**。

## 认可场景

2026-09-21，配置前缀 spkit→jevokit 重构（破坏性变更）讨论下一版版本号时，用户原话："前面两个数字是对齐 springboot 3.5 的，后面两个数字才是本项目的版本……破坏性变更第三位数字增加，可以打成 3.5.1.0"。

## 反例（什么算违背）

- 破坏性变更只递增第四位（3.5.0.0 → 3.5.0.1 却改了配置契约）
- 前两段与所依赖的 Spring Boot 版本线脱钩（Spring Boot 还是 3.5 却把库升到 3.6）
- SNAPSHOT 阶段版本不遵循同套语义（如破坏性改动期间主干停在 3.5.0.x-SNAPSHOT）

## 参考实现

- 3.5.0.0：首发（Spring Boot 3.5.16，配置前缀 spkit.*）
- 3.5.1.0（下一个破坏性版本）：配置前缀 jevokit.*，主干开发期版本号 3.5.1.0-SNAPSHOT
