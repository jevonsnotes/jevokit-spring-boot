# BUG 条目与处理进展必须向用户汇报

- 分类：沟通/流程
- 状态：已认可
- 适用范围：团队全角色——BUG 的发现、修复、复测、闭环各节点

## 偏好描述

成员上报的 BUG 条目不能只在领导与成员之间流转——领导必须把**BUG 详情（是什么/在哪/影响/根因/状态）**向用户汇报后再路由处理，闭环各关键节点（修复完成、复测结论）也要同步。用户是缺陷处置的知情方，不是事后才听总结的旁观者。

## 认可场景

2026-09-11，B 档测试重构中 eng-1 发现两个 core 模块产品缺陷（PageUtil 异步页号竞态、SecurityUtil 不可变集合崩溃），领导完成了派发修复与复测路由但未向用户汇报 BUG 本身，用户原话："什么bug，你要跟我也汇报下"。

## 反例（什么算违背）

- BUG 在成员→领导→成员之间闭环，用户只在终期总结里看到一句"修了 N 个 bug"
- 汇报只给结论（"已修复"）不给详情（现象/影响/根因）
- 修复或复测结论出来不同步，攒到最后一起说

## 参考实现

2026-09-11 的 BUG-1/BUG-2 汇报格式：位置 → 现象（实测数据）→ 根因本质 → 修复方式 → 当前状态（复测中）→ 闭环去向（教训沉淀）。
